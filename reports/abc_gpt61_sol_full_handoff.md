작성일: 2026-10-14, Asia/Seoul. 대상 브랜치: `2nd-yujin`의 로컬 작업 상태.

## 2. 전체 흐름

```text
원본 CSV / SOP PDF / 데이터시트 PDF (읽기 전용)
  └ 전처리: 문서 페이지·표·청크·해시
      ├ A: seed 노드·관계를 온톨로지에 맞는 RDF로 변환
      ├ B: 문서 등록 + 정비 8규칙 + 임계값 22규칙
      └ C: 선택한 SOP 60청크 → GPT-6.1 Sol → 원본 응답 저장
             → 스키마·ID·인용·좌표 검증 → B 연결 → 검토 양식
             ├ 자동 결과 고정 → 정답 86건 평가
             └ 검토 전 RDF 미리보기 → SHACL
추후: 사람 검토 → 승인된 최종 RDF → RAG / 탐지 / Agent
```

## 4. A: 기존 KG 변환

코드: `src/imaks_kg/kg/seed_to_rdf.py`. LLM 사용 없음.

Component 9개를 Station으로 매핑한다. 양방향 monitors 44행을 Station→Sensor의 hasSensor 22개로 정리하고 공정 흐름 3개를 feedsInto로 변환한다. 각 변환의 원본 CSV 근거를 남기고 예상과 다른 구조는 중단한다.

원본 Person·권한·Zone 클래스·이벤트 및 현재 단계 밖 관계를 그대로 승격하지 않는다. Zone은 Station 속성으로 다룬다. 원인 관계 발굴은 후속 단계다.

## 5. B: Rule·Document 노드 승격

코드: `src/imaks_kg/kg/promote_rules.py`. LLM 사용 없음. 정형 표를 결정적으로 변환한다.

- Document 7개: 문서 ID와 원본 문서 출처를 등록한다.
- SOP-003 정비 표: MAINT-01~08을 MaintenanceRule로 만들고 기존 센서 연결·우선순위와 대조한다.
- SOP-002 센서 표: ThresholdRule 22개를 만든다. 임계값은 Sensor 자체에 덮어쓰지 않고 별도 Rule에 둔다.
- 문서·페이지·표·행·열·셀 위치·원문 인용·해시를 Provenance로 남긴다.
- seed와 문서의 조치 문구가 다른 5건을 보존했다. 센서·우선순위 불일치는 없으며, 임계값 대조는 22센서 불일치 0건이다.

결과: `kg_build/rules_deterministic.ttl` 2,684트리플, Document 7·MaintenanceRule 8·ThresholdRule 22·Provenance 240. A+B 합본 3,166트리플.

## 6. C: GPT-6.1 Sol 호출 구현

주요 코드:

- `src/imaks_kg/extract/llm_openai.py`: OpenAI Responses API 요청·응답·오류 처리.
- `src/imaks_kg/extract/run.py`: 입력 준비, 비용 추정, 승인, 호출, 결과 저장·검증·병합.
- `schema.py`, `validate.py`: 구조·허용 ID·원문 인용·위치 검사.
- `merge.py`, `review.py`, `to_rdf.py`: B 연결·사람 검토·RDF 변환.
- `approval.py`, `ledger.py`, `locks.py`, `resume.py`: 시도 상한·해시 장부·잠금·이어하기.

| 설정 | 실행 값 |
|---|---|
| 공급자 / 모델 | OpenAI / `gpt-6.1-sol` |
| API | `POST https://api.openai.com/v1/responses` |
| 출력 형식 | `text.format` JSON Schema, `strict: true` |
| 추론 수준 | `low` |
| 최대 출력 | 요청당 16,000토큰, 추론 포함 |
| 요금 등급 | `service_tier: default` (표준) |
| 서버 저장 요청 | `store: false` |
| 호출 간격 | 1초 |
| 자동 전환 / fallback | 없음 |
| 미전송 설정 | temperature, top_p, seed |
| 타임아웃 | 600초 |
| 내부 자동 재시도 | 없음; 공통 정책에서만 시도를 기록하고 제한 |

키는 환경변수 우선, 없으면 로컬 `.env`의 `OPENAI_API_KEY`만 읽는다. 키 값은 요청 저장 파일·보고서에 넣지 않는다. 실제 모델 이름을 응답에서 확인한다. Gemini는 CLI 실행 선택에서 제거했지만 기존 어댑터 파일과 과거 실행 기록은 보존돼 있다. Anthropic은 명시 선택 경로만 남아 있으며 이번 실행에는 사용하지 않았다.

401/403과 결제·크레딧 오류는 전체 중단한다. 속도 제한 429와 503만 상한 안에서 재시도한다. 타임아웃·연결 오류·500/504처럼 처리·과금 여부가 불명확하면 자동 재시도 없이 중단한다. 응답 본문은 해석 전에 저장한다.

## 7. 프롬프트와 추출 필드

Role / Task / Example 3단 프롬프트 v1을 사용했다. 실제 seed의 센서·스테이션 ID를 허용 목록으로 넣는다. 예시 확인 상태는 CONFIRMED다.

예시 출처는 SOP-001 RULE-ST01-02, SOP-004 RULE-ACCESS-02, SOP-003 WRH01 관련 표다. 사용자가 예시 2의 `detection` 유지와 예시 3의 MaintenanceRule 분류를 확정했다. 실제 문서 예시와 평가 대상이 겹치므로 이를 독립 holdout으로 해석하지 않는다.

출력 필드: class(4분류), conditionText, responseText, ruleSeverity, sensors, targetStations, sourceQuote, ruleIdInText, actionSteps. 반환된 후보마다 원문과 인용 위치를 검증한다. 검증 통과는 의미·수치·운영 조치의 완전 정확성을 보장하지 않는다.

## 8. 60청크의 의미와 실제 실행

청크는 GPT에 보내는 문서 조각이다. 60은 문서 수·규칙 수·정답 수가 아니다. 본문·규칙 문장·표를 나눈 단위이며 한 청크에서 0건 또는 여러 규칙이 나올 수 있다.

현재 C 입력은 SOP만 허용한다. SOP-002의 11개 표 청크는 B에서 처리하므로 C에서는 제외했다. 데이터시트 15청크도 C에서는 제외하고 문서 등록 및 수치 충돌 확인 경로로 다룬다. 즉 전처리 86청크 = C 대상 60 + 제외 26이며, 이 86은 정답 규칙 86건과 별개다.

전체 실행 ID: `gpt61-sol-full-20261014`. 별도 시험 ID: `gpt61-sol-smoke-20261014`. 전체 실행은 시험 응답을 재사용하지 않고 60청크를 모두 새로 호출했다. 기존 Gemini 결과와 섞지 않았다.


| 문서 | GPT 입력 청크 | GPT 원본 규칙 |
|---|---:|---:|
| SOP-001 | 35 | 33 |
| SOP-002 | 10 | 1 |
| SOP-003 | 4 | 11 |
| SOP-004 | 11 | 35 |

| GPT 원본 분류 | 건수 |
|---|---:|
| AccessRule | 37 |
| MaintenanceRule | 11 |
| OperationalRule | 31 |
| ThresholdRule | 1 |

전체 실행: 60/60 성공, 후보 80건, 코드 검증 거부 0, 재시도 0, 다른 모델 fallback 0, B 재확인 8, 새 규칙 72, B 값 충돌 0.
실행 UTC: `2026-10-14T13:26:38+00:00` ~ `2026-10-14T13:32:56+00:00`. 한국 시간은 UTC+9다.

### 중복·세분화 관찰 — 반드시 후속 검토할 것

`meta.json`의 `combination_checks.ok`는 **false**다. duplicate_identifiers는 없지만 동일 인용 위치를 사용하는 후보가 여러 개 있고, RULE-CHM01-03 인쇄 ID가 여러 청크에서 발견됐다.

이 조합 검사 실패는 전체 실행 완료 상태와 다르다. 현재 코드가 이 검사를 강제 중단하는 경우는 이어하기로 응답을 합칠 때다. 이번 실행은 재사용 0건이라 status=completed로 끝났다. 따라서 “거부 0건”이나 “SHACL PASS”를 “중복·의미 품질까지 모두 PASS”라고 표현하면 안 된다.

동일 인용에서 여러 원자 규칙이 나온 경우와 실제 중복을 사람이 구분해야 한다. 평가 기준에 따라 분할 예측을 임의로 합치거나 제거하지 않았고, 첫 점수를 그대로 보존했다.

## 9. 평가 기준: 사용자 제공 두 Markdown 문서

기준 원문은 `docs/eval_definition_F1_content.md` 및 `docs/eval_definition_team_summary.md`에 복사했다. 사용자 파일의 내용을 기준으로 사용했다.

1. 유사도 문장은 condition + 공백 + action. ID·인용·클래스는 포함하지 않는다.
2. 임베딩은 `sentence-transformers/all-MiniLM-L6-v2`, revision `1110a243fdf4706b3f48f1d95db1a4f5529b4d41`. 모델 파일 해시 확인 후 로컬 CPU로 실행한다.
3. 같은 문서 안에서만 비교한다.
4. 코사인 ≥ 0.6인 쌍이 유효하다. 구현에는 경계의 부동소수 오차용 1e-9 허용치가 있다.
5. Hungarian 일대일 할당: 유효 매칭 수 최대화 후 유효 쌍의 유사도 합 최대화. 무효 쌍의 유사도는 목적 함수에 기여하지 않는다.
6. 클래스는 매칭 제한이 아니다. 매칭 뒤 혼동표·분류 일치 F1을 보고한다.
7. 주 보고는 SOP 예측 전체와 원본 정답 86건 전체. 미처리 정답은 FN. 데이터시트 예측은 FP에 넣지 않고 개수로 보고한다.
8. 0.5/0.7 임계값 민감도를 별도로 보고하며 주 점수는 0.6으로 고정한다.
9. 예측 해시·정의서·버전·모델·메타데이터를 `pre_evaluation_lock.json`에 기록한 뒤 정답을 읽는다. 정답 문서 ID가 알 수 없으면 중단한다.
10. 사람 수정본과 자동 결과를 구분하고 다른 추출 모델을 섞지 않는다. 개별 매칭 목록은 로컬에 보존한다.

평가 구현은 `src/imaks_kg/eval/`이며, 실행 프로그램은 `eval/evaluate_pipeline.py`다. 평가기의 문서별 매칭·분모·범위·잠금 테스트 27개를 통과했다. 기존 `eval/evaluate_rules.py`의 load_b를 B 입력 변환에 활용하지만 이번 점수는 그 파일의 기존 총 코사인 최대화 CLI로 계산하지 않았다. 기존 평가 CLI와 `rule_matching.py`는 이번 기준의 실행 진입점이 아니므로 사용하지 말 것.

**아직 하지 않은 보조 확인:** 정의서에서 제안한 단순 이어 붙이기와 `Condition: ... / Action: ...` 두 문장 구성의 민감도 비교는 실행하지 않았다. 수치·부등호의 개별 정답 정확도 진단도 이번 첫 집계에서 계산하지 않았다. 이번 F1을 수치 정확도라고 부르면 안 된다.

## 10. 평가 대상 네 종류와 추가 집계 정책

| 이름 | 의미 | 예측 수 |
|---|---|---:|
| C_automatic_raw | GPT 원본 규칙. 검증 결과에 따른 선택적 삭제 없음 | 80 |
| B_deterministic | 코드로 변환한 정비 8 + 임계값 22 | 30 |
| B_plus_C_pipeline | 기존 구축 파이프라인, B 30 + C 새 규칙 72 | 102 |
| B_plus_C_union | B 30 + GPT 원본 80, 재확인 중복도 포함 | 110 |

B+C pipeline의 B 재확인 8건 단일 집계는 두 평가 문서에 직접 규정된 사항이 아니라 **프로젝트의 추가 집계 정책**이다. 같은 문서·같은 인쇄 ID에 대해 추출 시 기록된 B 연결을 사용하며 정답 매칭 결과로 정한 것이 아니다. B 내용은 그대로 유지하고 C의 재확인 근거를 연결한다. 다른 분할 예측은 합치지 않는다. 정책 영향 확인용 union 점수도 함께 공개한다.

B의 수치형 ThresholdRule은 평가 문장에 센서·명목값·warn/crit·단위를 고정 방식으로 직렬화한다. C의 생성 문장과 표현 방식이 달라 유사도에 영향을 줄 수 있다. 이를 정답 문구에 맞춰 사후 수정하지 않았다.

## 11. 첫 정량 결과

| 평가 대상 | 예측 | 정답 | TP | FP | FN | Precision | Recall | F1_content |
|---|---:|---:|---:|---:|---:|---:|---:|---:|

| C_automatic_raw | 80 | 86 | 49 | 31 | 37 | 0.612500 | 0.569767 | 0.590361 |
| B_deterministic | 30 | 86 | 20 | 10 | 66 | 0.666667 | 0.232558 | 0.344828 |
| B_plus_C_pipeline | 102 | 86 | 61 | 41 | 25 | 0.598039 | 0.709302 | 0.648936 |
| B_plus_C_union | 110 | 86 | 61 | 49 | 25 | 0.554545 | 0.709302 | 0.622449 |

TP는 유효 매칭 수, FP는 매칭되지 않은 예측, FN은 매칭되지 않은 정답이다. Precision=TP/예측 수, Recall=TP/86, F1=2PR/(P+R).

전체 구축 결과 B+C pipeline은 F1 **0.648936**, GPT 단독은 **0.590361**, B 기준선은 **0.344828**이다. 서로 평가 입력이 다르므로 차이를 모델 성능 향상만으로 설명하면 안 된다.

### 문서별 B+C pipeline

## 16. 사람이 검토할 내용과 후속 작업

1. 원본 문서만 근거로 `review_round1.csv`를 검토한다. 조건·조치·분류·센서·인용·중복을 확인한다. 편집 가능 필드는 코드의 EDITABLE 목록을 따른다. B 병합 후보는 B 값 보존 때문에 편집 범위가 제한된다.
2. 동일 인용 분할과 RULE-CHM01-03의 여러 청크 출현을 우선 검토한다. 정답 매칭 결과를 보고 첫 예측의 문장·건수를 바꾸지 않는다.
3. 2차 검토 양식을 생성하고 필요한 표본·판정을 완료한다. LLM이 사람 이름으로 accept를 자동 입력하지 않는다.
4. 승인 후 apply_review와 최종 to_rdf를 실행한다. 최종 그래프 SHACL을 다시 검사한다. 검토 전 첫 점수는 그대로 남기고 검토본 평가를 따로 보고한다.
5. 문장 구성 민감도·수치 진단 등 아직 하지 않은 보조 분석을 필요 시 새 분석으로 추가한다.
6. 다음 단계인 벤치마크 문항 작성·Vector RAG 기준선·룰 기반 탐지기는 별도 구현한다. 이번 86규칙 평가는 질문 답변 성능 평가가 아니다.

## 17. 후속 LLM에게 전달할 핵심 제약

- GT를 프롬프트·청킹·규칙 수정에 사용하지 말 것.
- F1의 FP/FN을 곧바로 실제 운영 오류·미탐이라고 단정하지 말 것.
