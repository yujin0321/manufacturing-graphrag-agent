# 규칙 참조를 명시적으로 표현하는 실험

2026-10-27. 원래 예원 v2 KG(2,806트리플)는 고정하고, SOP-001 규칙 본문 24개 청크에 한정해 텍스트 참조 조회와 별도 RDF 관계 조회를 비교했다. 모델·API 호출 및 답변 생성은 없다. 실험 후보를 실제 GraphRAG에 반영하지 않았다.

## 1. 질문과 비교 설계

질문: “관계를 명시적으로 표현하면 규칙 참조의 방향·의미·출처를 더 명확하게 조회하고 검증할 수 있는가?”

| 방식 | 입력과 처리 | 비교 목적 |
|---|---|---|
| A 기존 텍스트 참조 | 현재 graph_v2의 조건·조치 텍스트 및 연결 원문에서 다른 규칙 ID를 찾는 식을 재현 | 현재 검색용 참조의 범위 확인 |
| B 명시적 텍스트 파서 | 같은 범위의 원문에서 `verify RULE-…` 또는 `check RULE-…` 지시만 추출 | 의미를 좁힌 효과와 RDF 표현 효과를 구분 |
| C 후보 RDF | B가 뽑은 같은 연결을 requiresRuleCheck와 출처 주장으로 저장 | 구조 조회·제약 검증 확인 |

A는 기존 함수의 텍스트 매칭 식을 사용한 **범위 제한 연결 열거**다. 실제 검색 순위, 시드 선택, 최대 방문 수, 최종 답변까지 재실행한 비교가 아니다. 역방향도 열거된 연결을 역조회한 것이며 기존 GraphRAG가 같은 역방향 탐색을 직접 수행한다는 뜻은 아니다.

B/C는 같은 연결을 사용하므로 의미 추출 개선을 RDF 고유 효과로 오인하지 않도록 했다. B의 정규식은 좁은 구문만 지원하며 일반적인 명령문 이해기나 온톨로지 자동 학습기가 아니다. 원문을 검토한 단일 명시 참조를 기대값으로 쓴 개발 실험이다.

## 2. 제안한 표현

```text
RULE-ST04-03 ── requiresRuleCheck ──→ RULE-ST02-04
```

의미: 출발 규칙이 대상 규칙을 확인하도록 **명시적으로 지시**한다. 인과관계, 실제 점검 실행, 양방향 동치 관계가 아니다.

두 끝점은 기존 v2의 `candidate-SOP-001::RULE-ST04-03`, `candidate-SOP-001::RULE-ST02-04` 노드를 사용한다. 기존 노드를 복제하거나 기본 KG를 수정하지 않았다. 추가 관계의 IRI는 실험 전용 이름공간에 둔다.

조건 “작업자 명령 없이 SPD <1.00 m/s”는 기존 출발 규칙과 원문에 남는다. requiresRuleCheck 관계만 떼어 무조건적인 확인 지시로 해석해서는 안 된다.

후보 그래프에는 직접 관계 1개와 ReferenceClaim 1개에 관한 타입·출발점·대상·청크 ID·인용문·청크 해시를 저장했다. 총 7트리플이다. 스키마와 SHACL은 별도 파일로 저장했다.

## 3. 조회 결과

| 검사 | A 기존 텍스트 | B 명시적 파서 | C 후보 RDF |
|---|---|---|---|
| 범위 내 연결 수 | 7 | 1 | 1 |
| ST04-03에서 확인하는 규칙 | ST02-04 | ST02-04 | ST02-04 |
| ST02-04를 확인하도록 지시하는 규칙 | ST04-03 | ST04-03 | ST04-03 |

C는 실제 SPARQL 정방향·역방향 조회도 실행해 결과를 확인했다. B와 C의 관계 쌍은 정확히 동일했다.

A의 나머지 여섯 연결은 다음과 같다.

| 출발 규칙 | 연결된 규칙 |
|---|---|
| RULE-CHM01-01-CRITICAL | RULE-CHM01-01 |
| RULE-CHM01-02-DESICCANT | RULE-CHM01-02 |
| RULE-CHM01-03-UNAUTHORIZED | RULE-CHM01-03 |
| RULE-RND01-02-CRITICAL | RULE-RND01-02 |
| RULE-ST03-02-CRITICAL | RULE-ST03-02 |
| RULE-WRH01-01-CRITICAL | RULE-WRH01-01 |

분할된 추출 규칙의 연결 원문에 원래 규칙 ID가 등장하면서 만들어진 검색 참조다. A는 애초에 ‘다른 규칙 확인 지시’만 찾는 기능이 아니므로 이를 기존 검색의 오답 6개라고 세면 안 된다. 다만 이 연결들을 모두 requiresRuleCheck로 바꾸면 의미 오류가 된다.

**조회의 결론:** 특정 방향 조회는 기존 방식도 해결했다. 명시적 관계의 장점은 어떤 종류의 연결인지를 표현하고 조회 조건을 고정할 수 있다는 점이다. 명시적 텍스트 파서도 같은 결과를 얻었으므로 RDF의 정확도 향상을 입증한 것은 아니다. 속도·메모리 우위도 측정하지 않았다.

## 4. 검증 실험

정상 후보는 기본 v2와 합쳐 검사했을 때 후보용 SHACL과 원문 대조를 통과했다. 원문 대조는 보존된 원문 청크·해시·좁은 파서의 추출 방향과 비교하는 별도 검사이며, 독립 전문가의 의미 판정은 아니다.

원래 v2의 SHACL을 확장·덮어쓰지 않고 실험 전용 제약을 사용했다. 주요 제약은 Rule→Rule, 출처 주장과 직접 관계의 일치, 출처 필수값, 자기 참조 금지다. 자기 참조 금지는 이번 실험의 설계 선택이며 모든 도메인 규칙의 보편 법칙은 아니다.

| 인위적으로 삽입한 오류 | SHACL | 원문 대조 |
|---|---|---|
| 인용문 제거 | 검출 | 검출 |
| 방향 반전과 주장 끝점을 함께 변경 | 통과 | 검출 |
| 형식은 맞지만 값이 틀린 SHA-256 | 통과 | 검출 |
| 가짜 인용문 | 통과 | 검출 |
| 대상에 Sensor 노드 지정 | 검출 | 검출 |
| 자기 자신을 확인하도록 연결 | 검출 | 검출 |
| 근거 주장 없는 추가 간선 | 검출 | 검출 |

구조 검사로 4종, 원문 대조까지 포함하면 7종 모두 검출했다. 이것은 설계한 오류 주입 사례의 결과이며 실제 데이터 전체 오류 검출률 100%를 뜻하지 않는다. **SHACL 통과만으로 방향·인용의 사실성을 보장하지 못한다.**

파서 대조 입력에서는 `verify RULE-ST02-04`를 찾고 단순 공동 출현은 제외했다. 반면 `consult the guidance in RULE-ST02-04` 같은 지원하지 않는 표현도 놓쳤다. RDF 저장은 이러한 상류 추출 누락을 자동으로 해결하지 못한다.

## 5. 판단과 적용 범위

이번 실험으로 확인한 기여는 다음과 같다.

1. 검색용 일반 참조와 명시적 확인 지시를 구분할 수 있다.
2. 동일 관계를 정방향·역방향으로 구조 조회할 수 있다.
3. 관계의 끝점·출처 필수값·직접 간선과 주장의 일치 여부를 SHACL로 검사할 수 있다.
4. 의미 방향과 인용의 사실성은 원문 대조가 추가로 필요하다.

**채택 판단은 보류한다.** 기준 v2와 실제 검색 코드는 그대로다. 후보는 온톨로지 표현의 명확성·검증 가능성을 보여주는 별도 실험으로 보존한다. 실제 적용이 필요해질 때 원문을 고정한 검색 회귀와 더 다양한 문서·참조 표현을 확인해야 한다. 이번 결과만으로 답변 정확도 개선이나 새로운 제조 관계 발견을 주장하지 않는다.

## 6. 산출물과 재현

- 실행 코드: `scripts/compare_explicit_rule_reference.py`
- 로컬 산출물: `kg_build/explicit_reference_20261027/`
- `candidate_ontology.ttl`: 후보 관계·출처 주장 어휘
- `candidate_shapes.ttl`: 후보 전용 제약
- `candidate_overlay.ttl`: 1개 관계와 출처 주장, 기본 v2와 분리
- `reference_manifest.json`: 원문 기반 관계와 출처
- `summary.json`: 세 방식 조회·오류 주입·파서 대조·해시
- `shacl.txt`: 정상 후보의 검사 결과
- `complete.json`: 산출물 해시 봉인

기존 가상환경에서 `PYTHONPATH=src`로 설정하고 `python scripts/compare_explicit_rule_reference.py`로 실행한다. 원문 청크와 v2 KG, 기존 RDFLib·pySHACL이 필요하다. 기존 산출물 폴더가 있으면 덮어쓰지 않고 중단한다. 재실험은 새 버전 경로로 구분한다.

모델 호출·다운로드·추가 패키지 설치는 없다. 기존 v2 KG SHA-256은 `8ab82a866135afd1335caab06fe6e6e223d7b1ea37195e3fe6509cbbd407ef51`이며, 온톨로지 v1·기존 shapes·검색 코드의 해시도 기록했다. 이번 파일은 아직 커밋·푸시하지 않았다.
