## 5. 이번에 확정된 핵심 결정 (요약)
- **요청 단위:** 문서 1개 = 요청 1개. 표 행·열 번호는 1부터(헤더 = 행 1).
- **Example:** 영어, 가상. `example_check` 4종(정답 고유 문구, 원문 5단어, 데이터셋 어휘, 해시)을 통과해 등록해야 `run`이 실행된다(현재 `example_v1.txt` 등록됨, 해시 `edbf73a7…`).
- **점수 실행(`run_mode = "scoring"`)은 체인에 모델 하나만.** fallback은 운영 실행에만. 샘플링 매개변수(온도 등)는 보내지 않는다. 재현성은 응답 고정·캐시로 보장.
- **재시도:** 429·408·5xx만 지수 백오프(1·2·4·8초)로 최대 4회 재시도(총 5회 시도). 400은 다음 모델로, 크레딧·인증 오류는 해당 공급자만 중단.
- **인용 일치:** 공백류를 하나로 정규화해 비교(숫자·단어·대소문자·구두점은 엄격). `quote_match_rate`가 예선 1차 관문의 "인용 일치율".
- **중복 인쇄 ID:** 같은 문서에서 반복되면 `-2`, `-3` 접미사(`split_from_printed_id`).
- **MAINT ID 충돌:** ③ seed 정비 규칙과 identifier가 겹치는 LLM 규칙은 TTL에서 제외하고 `identifier_conflicts.json`에 기록(병합 안 함).
- **평가:** 같은 문서 안에서만 매칭, 코사인 >= 0.6, 유효 매칭 수 최대화 후 **유효 쌍의 유사도 합** 최대화, 클래스는 매칭 제한 없이 혼동표로 분리. 주 보고 = 정답 86건 분모. 데이터시트 예측은 범위 밖으로 따로 집계. 정답은 예측을 고정(`pre_evaluation_lock.json`)한 뒤에만 읽는다.
- **문서 분할:** 예선 `SOP-003 + 004`(정답 30건 노출), 최종 `SOP-001 + 002`(56건). 데이터시트는 채점되지 않는다(정답에 행 없음, 직접 확인).
- **모델 후보:** `gemini-3.1-flash-lite`, `gemini-3.8-flash`, `gpt-6.1-sol`(모두 실제 모델 목록에서 확인).
- **금지어 규칙:** 누수 점검이 `severity`, `ground_truth`(평가 폴더 밖), `status`(JSON 키)를 막는다. 우회하지 않고 이름을 바꾼다(`ruleSeverity`, `answer_key_supplied`, `coverage_status`). `kg_build/extraction/`와 `preprocessed/documents/`만 본문 값 검사 예외.

## 6. 다음 작업 (순서)
1. **캐시 우회 보강 (예선 전에 필수).** 같은 설정으로 반복 실행하면 캐시가 같은 응답을 돌려줘 "3회 실행 일관성" 측정이 무의미해진다. 반복마다 캐시를 우회하는 옵션(예: `--no-cache` 또는 run id를 캐시 키에 포함)을 추가하고 시험한다. 구현 -> 독립 검증.
2. **모델 예선.** 모델 3개 x `SOP-003,SOP-004` x 3회(약 18회 호출). 설정은 `config/extract.<모델>.toml`. 예: `run --config config\extract.gpt-6-1-sol.toml --docs SOP-003,SOP-004 --run-id prelim-gpt61sol-r1`. 평가: `python -m imaks_kg.eval --predictions kg_build\extraction\<run>\predictions.jsonl --out-dir evaluation\<run> --meta kg_build\extraction\<run>\eval_meta.json --processed-docs SOP-003,SOP-004`. **정답 노출 문서로 표기한다.**
3. **선정 규칙(결과 보기 전 확정):** 1차 관문 JSON 파싱 성공률 >= 95%와 인용 일치율 >= 95% -> 2차 F1_content가 가장 높은 모델(차이가 작으면 3회 일관성) -> 3차 비용·무료 한도. 기록 항목: F1_content, 파싱 성공률, 인용 일치율, 3회 일관성, 토큰(사고 토큰 포함), 비용, 지연, 재시도 횟수, 503·타임아웃 횟수, 잘림 비율, 생각 수준, 모델 이름·날짜·프롬프트 버전. 표로 `work_log.md`에 남긴다.
4. **최종 실행.** 선정한 모델 하나로 `SOP-001,SOP-002` -> 사람 검토 1단계(표시 항목)·2단계(약 20% 표본, SOP 원문만 기준) -> `to-rdf` + SHACL -> 평가 -> **첫 정량 결과**. 프롬프트 수정은 첫 점수를 기준선으로 고정한 뒤 최대 2회, 오류 유형만 근거로 하고 이유를 기록한다. 데이터시트와 SOP-002의 충돌 수치는 출처와 함께 둘 다 기록한다.
5. **평가 정의서를 팀에 제안**하고 같은 조건으로 재평가(합의 사항은 정의서 §8).

## 8. 작업 방식 (지훈과의 약속)
- 설명은 **쉬운 말, 비유, 추천안, 위험도** 순서로. 선택지는 추천을 먼저.
- **구현은 구현 에이전트, 검증은 독립 검증 에이전트**(체크리스트 기준). 구현 보고서를 검증 근거로 쓰지 않는다.
- `CLAUDE.md`·공유 점검 도구·체크리스트·`.claude/` 수정은 **전후를 보여 주고 승인받은 뒤 백업하고 반영**한다. 점검 도구와 충돌하면 우회하지 않고 알린다.
- 확인하지 못한 것은 "미확인"으로 적는다. 도구가 성공했다고 해도 결과를 다시 읽어 확인한다.
- 정답 파일은 `eval/gold.py`와 점검 스크립트만 읽는다. 규칙 문장을 출력·기록하지 않는다.
- 실제 API 호출 전에 알리고, 키는 채팅·코드·로그에 남기지 않는다. 커밋은 작업을 마무리한 뒤 한꺼번에, push는 지훈이 승인할 때만.
- 팀원 브랜치 비교 결과(`reports/branch_*.md`)는 로컬 전용이다.
