# 제조 지식그래프 A·B·C 및 86규칙 평가 최종 구현 설명

작성일: 2026-10-14. 이 파일은 실행·평가가 끝난 뒤 결과를 채워 최종본으로 저장한다.

## 1. 전체 구조와 범위

전처리 → A(기존 설비 구조 변환) → B(표 규칙·문서 등록) → C(LLM 문장 규칙 추출 및 검토) → 평가(정답 86규칙 대조).

A·B는 모델 없이 코드로 변환한다. C는 Gemini를 사용한다. 평가는 로컬 SBERT를 사용하며, 추출과 분리된 프로그램이다. 현재 작업은 GraphRAG와 Agent가 사용할 지식을 만드는 범위이며, Neo4j 검색·인과 후보 추론·최종 Agent 답변까지 구현한 것은 아니다.

## 2. 전처리: A·B·C의 입력 준비

센서 CSV 211,200행을 측정 입력, 임계값, 평가용 라벨, 원래 시간 라벨로 나눴다. 측정값은 원본 그대로 보존하며 이상값 삭제·보간·평활화는 하지 않는다. 인과 분석 입력에는 정답 라벨이나 임계값을 넣지 않는다.

SOP 4개와 데이터시트 3개 PDF에서 본문·표를 추출하고 문서·페이지·위치·원문 해시를 저장한다. Symbol 폰트에서 깨진 화살표·부등호 등을 제한적으로 복원하고 수정 기록을 남긴다. 규칙·표·본문 단위의 청크를 만들며, 정답 규칙 파일은 청킹과 프롬프트에 사용하지 않는다.

입력과 출력, 전처리 코드의 해시를 preprocess_lock으로 확인한다. 해시는 변경 여부를 확인하는 수단이며, 모든 파일을 함께 고치는 공격을 혼자 막는 서명은 아니다.

## 3. A: 기존 KG 변환

### 방법과 모델

`src/imaks_kg/kg/seed_to_rdf.py`가 기존 nodes.csv와 edges.csv를 온톨로지에 맞춰 RDF로 변환한다. 모델 호출은 없다. RDF는 “주체–관계–대상” 형태의 지식 표현이고, TTL은 이를 저장하는 파일 형식이다.

원본 Component 9개를 Station으로 매핑하고 센서 22개를 연결했다. 원본 monitors의 양방향 44행을 Station→Sensor의 hasSensor 22개로 정리하고, 공정 흐름 3개를 feedsInto로 변환했다. 원본의 Person·권한·안전 이벤트 등은 이번 범위에서 제외하고, 이상 이벤트는 후속 단계 경로로 분리했다.

모든 변환은 원본 CSV 행을 찾아갈 수 있는 출처 정보를 남긴다. 누락·중복·알 수 없는 종류가 나오면 조용히 넘기지 않고 멈춘다.

### 확인한 결과

- `kg_build/seed.ttl`: 482트리플.
- Station 9개, Sensor 22개, hasSensor 22개, feedsInto 3개, Provenance 56개.
- 기존 독립 검증 PASS. 이번 작업에서 실제 파일을 다시 파싱하고 A+B SHACL 검사를 통과했다.

## 4. B: Rule·Document 노드 승격

### 방법과 모델

`src/imaks_kg/kg/promote_rules.py`가 전처리된 문서 표를 정해진 구조로 읽는다. LLM 없이 결정적으로 변환한다.

문서 7개를 Document로 등록한다. SOP-003의 유지보수 표에서 조건·조치를 읽어 MAINT-01~08을 MaintenanceRule로 만들고, 원본 CSV의 센서 연결·우선순위와 대조한다. SOP-002의 센서별 표를 ThresholdRule로 만들고 raw 센서 임계값 및 기존 seed 수치와 대조한다.

임계값은 Sensor 자체에 붙이지 않고 별도 규칙 노드로 연결한다. 출처는 문서·페이지·표·행·열·셀 좌표·인용·해시로 기록한다. 문구나 수치가 다른 것은 보고서에 남기며 임의로 통일하지 않는다.

### 확인한 결과

- `kg_build/rules_deterministic.ttl`: 2,684트리플.
- Document 7개, MaintenanceRule 8개, ThresholdRule 22개, Provenance 240개.
- A+B 합본: 3,166트리플. SHACL 적합.
- 유지보수 8건 중 원본 seed와 SOP 조치 문구가 다른 5건은 비교표에 보존했다. 센서·우선순위 차이는 없다.
- SOP-002와 seed·센서 임계값 대조는 22센서에서 불일치 0건이다. 데이터시트와 SOP의 별도 충돌은 C의 충돌 보고 경로로 남긴다.

## 5. C: LLM 규칙 추출

### 방법과 모델

`src/imaks_kg/extract/`가 SOP의 자연어를 규칙 후보로 바꾼다. 실제 모델과 실행 결과는 아래 결과 표에 기록한다.

Role/Task/Example 프롬프트와 JSON 출력 스키마를 사용한다. 규칙은 OperationalRule, ThresholdRule, MaintenanceRule, AccessRule 중 하나로 분류하고 조건·조치·센서·공정·원문 인용 등을 받는다.

SOP-001·003·004의 모든 청크와 SOP-002의 표 밖 청크를 대상으로 한다. SOP-002 표는 B가 이미 변환했으므로 제외한다. 데이터시트는 Gemini에 보내지 않고 수치 충돌 비교에만 사용한다. 전체 대상은 60청크다.

자동 검사는 JSON 구조, 실제 센서·공정 목록, 인용의 원문 일치, 문자 또는 표 좌표를 확인한다. B와 같은 규칙이면 새 규칙을 만들지 않고 재확인 출처만 붙인다. B의 규칙 값은 바꾸지 않는다. 차이가 있으면 충돌 기록을 남긴다.

검토는 원문 기반 제안과 사용자의 승인 기록을 구분한다. 1차 결정과 수정·보류에 대한 2차 결정을 보존하고, 완료된 검토 결과만 최종 RDF로 출력한다. 실제 검토 승인 범위와 일시는 최종 결과에 기록한다.

### 실행 안전성과 검증

- dry-run은 생성 호출 없이 입력·토큰 추정과 승인 ID를 만든다.
- 승인된 청크 수와 API 시도 수를 따로 제한한다. 청크당 최대 3시도, 실행당 재시도 최대 10회다.
- 호출 단계 저널을 남긴다. HTTP 200은 해석 전에 기록하고 원본 응답도 먼저 저장한다.
- 중단·전송 결과 불확실 시 승인을 사용량 확인 필요 상태로 잠근다. 비정상 종료 복구가 사용 가능 상태로 자동 복원하지 않는다.
- Windows 프로세스 간 잠금으로 동일 승인 동시 실행과 장부 동시 기록을 보호한다.
- 재시도와 청크 간 호출에 같은 페이서를 적용한다. 간격·backoff·서버 권고 대기를 함께 고려한다.
- 파일 해시를 외부 장부와 비교한다. 장부 자체까지 바꾸는 공격의 방어에는 별도의 이력 검토가 필요하다.
- 이번 로컬 전체 테스트는 281개 PASS(455.186초), 원본 불변 1,121파일 PASS, 누수 검사 PASS다.

## 6. 86규칙 정량 평가

### 방법과 모델

평가 전용 코드는 `eval/`에 있고 결과·별도 실행 환경·모델은 `evaluation/`에 둔다. 추출 프로그램이 평가 코드를 가져오거나 정답 CSV를 읽지 않는다.

모델은 `sentence-transformers/all-MiniLM-L6-v2`이며 CPU에서 오프라인으로 실행한다. 정확한 모델 revision과 라이브러리 버전, 평가 입력 해시를 저장한다. 정답 데이터는 외부로 전송하지 않는다.

주 평가는 B의 30규칙과 C의 새 규칙을 합친 결과다. C가 B를 재확인한 경우에는 B의 원래 내용으로 한 번만 센다. B-only와 검토 전·후 결과를 구분한다.

조건·조치 문장을 임베딩하고 cosine 유사도를 계산한다. 식별자·문서 ID·클래스 이름을 임베딩에 넣지 않는다. B 임계값 조건이 숫자 속성으로 저장된 경우 해당 속성을 명시적으로 직렬화한다. Hungarian 알고리즘으로 총 유사도가 최대인 1대1 대응을 찾은 후, cosine 0.6 이상인 대응을 TP로 센다. 한 규칙을 여러 정답에 중복 대응시키지 않는다.

- Precision = TP / 추출 규칙 수.
- Recall = TP / 86.
- F1_content = Precision과 Recall의 조화평균.
- 여기서 Coverage는 대응된 정답 규칙 비율로 Recall과 같다.

클래스별 수치와 대응된 규칙의 클래스 일치율도 별도로 보고한다. 예시에 나온 세 청크의 새 규칙을 제외한 민감도 수치도 제공하되, 이를 독립 holdout 성능이라고 부르지 않는다. 평가 전에 추출·검토 입력을 해시로 고정하고 이후 변경 여부를 다시 검사한다. 정답 대조 결과를 보고 추출·검토를 고치지 않는다.
