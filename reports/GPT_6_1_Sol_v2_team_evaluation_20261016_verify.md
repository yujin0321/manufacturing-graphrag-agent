## 2. 데이터와 구현 범위

iMAKS에서 전처리한 문서 본문·표를 사용했다. SOP-001~004 및 DS-ELEC-3300, DS-MECH-4400, DS-THERM-2200의 7개 문서를 각각 독립 요청으로 처리했다. API 입력은 원문 단위, 엔티티 목록, 프롬프트와 합성 Example이다. 정답 파일이나 목표 규칙 개수는 API에 넣지 않았다.

기존 KG의 Component 9개를 Station으로 매핑하고 Sensor 22개를 연결했다. 규칙은 OperationalRule, ThresholdRule, MaintenanceRule, AccessRule로 구분하고, 문서는 Document, 근거는 Provenance로 관리한다. Person·authorized_for·실제 이상 이벤트·인과관계 생성은 이번 단계의 결과에 포함하지 않는다.

## 3. 자동 추출 구현 과정

1. 원문·전처리 해시 검증 후 `documents.prepare()`로 문서별 패킷을 구성한다. `prepare_extraction_v2.py`가 원문과 엔티티 목록을 유지하면서 v2 프롬프트를 적용한다.
2. Python 표준 라이브러리 HTTP 클라이언트로 OpenAI Chat Completions API를 호출한다. 모델은 `gpt-6.1-sol`, JSON 출력, `max_completion_tokens=16000`, `store=false`다. temperature와 reasoning_effort는 지정하지 않아 서비스 기본값을 사용했다.
3. 각 문서는 대화 이력을 공유하지 않는다. 자동 재시도 없이 요청·원본 응답·요청 해시·사용 토큰을 보존하고, 저장된 응답은 재사용한다. 키는 환경변수에서 읽으며 저장소에 기록하지 않는다.
4. 응답의 규칙 클래스, 센서·설비 참조, 원문 인용의 정확한 포함 여부, 유한 숫자 여부를 검증한다. 중복 식별자는 문서 namespace와 part 번호로 구분하고 대응표를 저장한다. 조건·조치 문장은 수정하지 않는다.
5. 예측 JSONL의 SHA-256을 고정한다. 기존 구조 및 seed 정비 규칙과 결합해 RDF 후보 KG를 생성하고 `inference=none`으로 SHACL을 실행한다.
6. Colab CPU에서 고정 SBERT 모델로 코사인 행렬을 생성했다. 팀 기준 재채점은 해당 전체 행렬을 재사용해 매칭을 다시 계산했다. 모델을 다시 다운로드하거나 API를 재호출하지 않았다.

### v2 추출 정책

- 클래스는 숫자나 조치 단어가 아니라 원문 조항의 목적에 따라 판정한다. 운영 절차에 나오는 점검·정비 요청이 반드시 MaintenanceRule인 것은 아니다.
- 센서 임계값 표는 센서 한 행의 nominal·경고·위험 한계를 하나의 ThresholdRule로 묶는다. 이상 유형 정의는 유형별 규칙으로 추출한다.
- 같은 조건에 딸린 복수 조치는 하나로 유지한다. 서로 다른 조건·심각도에 다른 대응이 있을 때만 구분한다.
- 인원 제한·접근 자격·역할별 경보 확인 기한은 AccessRule로 분류한다.
- 본문·표에 반복된 사실은 중복 추출하지 않고, 단순 설명을 독립 규칙으로 과도하게 승격하지 않는다.
- 원문에 없는 일반 점검·통보 조치를 채워 넣지 않는다. 출처가 다른 충돌 값은 임의 통일하지 않는다.

## 4. 팀 평가 기준의 구현

### 입력과 유사도

예측의 `ruleClass/conditionText/responseText`를 공통 스키마의 `class/condition/action`으로 해석한다. `document_id`는 검증된 원문 단위의 문서 ID로 얻는다. 유사도 문장은 `(condition + " " + action).strip()`이며 ID·분류·인용문은 넣지 않는다.

임베딩은 `sentence-transformers/all-MiniLM-L6-v2`, revision `1110a243fdf4706b3f48f1d95db1a4f5529b4d41`을 사용한다. 정규화 벡터의 내적으로 코사인 유사도를 계산했다. 원본 정답 `source` 열은 SOP-001~004만 허용하며 알 수 없는 문서는 오류로 중단한다. 실제 정답은 SOP-001 29개, SOP-002 27개, SOP-003 11개, SOP-004 19개로 총 86개다. 데이터시트 정답 행은 없다.

### 매칭과 분모

- 같은 문서 안에서만 비교하며 **클래스는 주 매칭 제한에서 제외**한다.
- cosine≥0.6인 쌍만 유효하다. Hungarian 할당은 **유효 매칭 수를 먼저 최대화**하고 동률이면 **유효한 쌍의 유사도 합**을 최대화한다.
- 구현은 유효 쌍에 `B+cosine`, 무효·dummy 쌍에 0을 부여한다. `B=min(P,G)+1`이므로 유사도 합보다 유효 쌍 수가 우선한다.
- TP는 유효 매칭 수, FP=P−TP, FN=G−TP다. 클래스 일치 보조 지표는 이 배정 후 같은 클래스인 쌍만 TP로 세며 분모 P/G는 유지한다.
- SOP 예측 95개와 정답 86개 전체가 주 분모다. 데이터시트 5개는 범위 밖 예측으로 보고하고 FP에 넣지 않는다. 분할 예측을 평가 후 합치지 않는다.
- 작은 무작위 행렬 60개의 완전탐색 최적해 비교, 유효 매칭 수 우선, 무효 유사도 배제, 문서 제한 회귀 검사를 통과했다. 순수 Python Hungarian을 사용해 추가 설치를 피했다.

## 6. 보조 지표

### 매칭 후 클래스 혼동표

행은 정답, 열은 예측이다. 매칭된 78쌍만 포함하며 미매칭 항목은 제외한다.

| 정답 / 예측 | AccessRule | MaintenanceRule | OperationalRule | ThresholdRule |
|---|---:|---:|---:|---:|
| AccessRule | 17 | 0 | 0 | 0 |
| MaintenanceRule | 0 | 9 | 0 | 0 |
| OperationalRule | 0 | 0 | 25 | 0 |
| ThresholdRule | 0 | 0 | 0 | 27 |

매칭쌍 78개가 모두 같은 클래스여서 분류까지 일치 F1도 86.19%다. 전체 예측의 분류 정확도가 100%라는 뜻은 아니다.

### 임계값 민감도

| 임계값 | TP / FP / FN | F1 |
|---|---|---:|
| 0.5 — 참고 | 84 / 11 / 2 | 92.82% |
| **0.6 — 주 기준** | **78 / 17 / 8** | **86.19%** |
| 0.7 — 참고 | 61 / 34 / 25 | 67.40% |

민감도는 보고만 하며 주 점수 임계값을 변경하지 않았다.

매칭쌍의 센서 집합 일치율은 **73/78=93.59%**다. 센서 문자열을 대문자 영숫자로 정규화하여 underscore/hyphen 표기 차이를 제거한 뒤 집합 비교했고, 양쪽 빈 집합도 일치로 포함했다. 이 표기 정규화는 팀 정의서에 구체적으로 정해지지 않아 구현 선택으로 명시한다. 전체 필드 정확도는 아니다.

## 7. KG와 실패 분석

후보 KG는 2,806 트리플이며 모든 트리플에 근거가 있다. Station 9, Sensor 22, Document 7, 추출 Rule 100개를 포함한다. seed MaintenanceRule 8개는 별도로 남으며 추출 평가의 예측 수에 더하지 않았다. 구조·후보 SHACL은 통과했지만 사람 승인과 Neo4j 적재는 미완료다.

잔여 미매칭 17건·누락 8건의 원문 대조에서는 다음 유형이 관찰됐다.

- 원문에는 있지만 정답 목록에 없는 추가 규칙.
- 정답에는 조치가 포함됐지만 해당 원문에서 확인되지 않는 사례.
- 같은 원문 조항의 분할 단위와 일대일 배정 경쟁.
- 핵심 내용이 유사해도 표현·약어·필드 배치 차이로 코사인 기준 미달.

따라서 FP 전체를 환각, FN 전체를 실제 미추출로 단정하지 않는다. 점수에 맞춰 유효 규칙을 삭제하거나 정답 조치를 추출에 복사하지 않았다. 이 원문 대조는 AI 근거 검토이며 사람 최종 승인과 다르다. Main Entrance 범위 제외와 역할별 출입 허용에 별도 자격·교육 요건 연결은 후속 보완 대상이다.

SOP-002 F1 100%도 수치·부등호 정확도 보장이 아니다. 선행 원문 검토에서 정답과 원문 사이 임계값 4개 차이가 확인됐지만 원본 정답·추출을 바꾸지 않았다. 개별 정답 문장과 매칭 목록은 이 공유 보고서에 싣지 않는다.

## 8. 재현성과 제한 사항

| 항목 | 기록 |
|---|---|
| 팀 정의서 SHA-256 | `35be575441258dbf80d8909fd8083124d0aa523476b878c14e22f002920a3e94` |

| Colab 설치 지시 | sentence-transformers 3.4.1, scipy 1.15.2 |

1. **정답 노출:** 선행 개발·평가에서 정답을 본 이력이 있으며 v2는 오류 유형을 참고해 설계했다. API에 정답을 보내지 않은 것과 실험자의 정답 비노출은 다르다. 독립 시험으로 보고하지 않는다.
2. **사전 잠금:** 최초 평가의 예측 freeze는 있었으나 팀 정의서 해시 등을 포함한 완전한 사전 잠금은 없었다. 팀 재채점 직전 생성한 잠금은 retrospective로 표시했으며 소급하여 사전 통제를 주장하지 않는다.
3. **버전:** 실제 Colab 전체 라이브러리 버전 출력은 보존하지 못했다. 위 값은 설치 지시이며 실제 버전 확인 기록으로 주장하지 않는다. 로컬 재채점 Python/NumPy 버전은 공개 잠금 파일에 기록했다.
4. **문장 형식 민감도 미측정:** `Condition: …\nAction: …` 형식의 대체 임베딩이 없어 팀이 요청한 형식 비교는 미완료다. 주 점수는 단순 연결 형식으로 재계산했다.
5. **정답 접근 경로:** 팀 재채점 모듈은 `src/imaks_kg/eval/` 안에서 정답을 읽는다. 과거 Colab 패키징·원문 감사는 이 디렉터리 밖에서 평가 목적으로 읽었으므로 전 기간 경로 규칙 준수로 주장하지 않는다.
6. **재평가 범위:** 보존된 전체 코사인 행렬과 고정 예측/정답 해시를 검증하여 할당을 다시 계산했다. 임베딩 자체는 재생성하지 않았다.
7. **비공개 재현 입력:** 원문 데이터·응답·개별 예측·매칭은 로컬에 보존하며 Git에는 집계와 해시만 포함한다. 전체 재현은 같은 데이터와 고정 응답/행렬을 가진 팀 환경에서 가능하다. 새 API 호출은 비결정적이어서 같은 출력이 보장되지 않는다.

## 9. 결론

GPT-6.1 Sol v2는 팀의 동일 문서·클래스 비제한·유효 매칭 수 우선 평가에서 **F1_content 86.19%**를 얻었다. 자동 추출, 출처를 갖춘 후보 KG 구축, 개발셋 정량 평가를 완료했으며 사람 승인과 미측정 보조 확인은 남아 있다.
