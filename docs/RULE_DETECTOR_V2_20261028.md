# 룰 탐지기 v2 — KG에서 조건을 읽어 실행 + 이벤트 단위 평가

2026-10-28. v1(`detection/rules.py`)과 그 결과는 그대로 두고 `detection/kg_rules.py`를 추가했다.

## 바뀐 점

1. **조건을 KG에서 컴파일한다.** 규칙 노드의 `conditionText` + `appliesToSensor`를 작은 결정적 문법으로 해석한다. RULE-ST02-03의 명목값은 센서 노드가 아니라 같은 센서를 가리키는 SOP-002 ThresholdRule에서 가져온다(운영 규칙 → 센서 ← 임계값 규칙 조인).
2. **v1 표를 정답 대조용 테스트로 쓴다.** 사람이 검토한 30개 실행 조건과 KG 컴파일 결과가 하나라도 다르면 테스트가 실패한다. 개발 중 이 테스트가 문법 버그 2개를 잡았다(`for >15 min`의 15를 임계값으로 읽음, 명목값 위치).
3. **SOP-002 경고/위험 구간도 KG(ThresholdRule)에서 실행**하고 센서 메타데이터 CSV와 대조한다(차이 0건).
4. **train/validation/test 경계에서 지속 상태를 초기화하지 않는다.** 학습이 없으므로 구간은 보고용 표시일 뿐이다. 이 데이터에서는 결과가 바뀌지 않았다(문서 규칙 탐지 구간 43건이 v1과 동일).

미지원(추측하지 않음): RULE-ST04-03(작업자 명령 관측 불가), RULE-ST02-04(모니터링 지시), MAINT-01/02/06/08(DRIFT 기울기 미정의), SOP-003 상관 패턴 3개.

## 이벤트 단위 평가 (`scripts/evaluate_detector_events.py`)

정답 이벤트는 `row_labels.csv`에서 센서별로 연속된 비정상 라벨 구간이며 14건이다(데이터셋 이상 이벤트 수와 일치). 탐지 결과의 해시를 확인한 뒤에만 라벨을 읽는다.

| 규칙 계열 | 잡은 이벤트 | 오경보 | 중앙 지연 | 유형별 |
|---|---:|---:|---:|---|
| 문서 규칙(KG 컴파일) | 12/14 | 0 | 0.5분 | SPIKE 3/3, OUT_OF_RANGE 4/4, STUCK 1/1, DRIFT 4/5, CORRELATED 0/1 |
| SOP-002 경고 구간 | 12/14 | 1 | 0.5분 | DRIFT 5/5, STUCK 0/1 |
| SOP-002 위험 구간 | 4/14 | 0 | 0분 | SPIKE 3/3 |
| 전체 | 13/14 | 1 | 0.5분 | CORRELATED 0/1만 미탐 |

읽는 법:
- **놓친 1건은 GT-0009**(ST04 속도 저하, ST02 전류 드리프트가 원인인 상관 이상)이다. 이를 잡는 규칙(RULE-ST04-03)은 작업자 명령 정보가 없어 실행할 수 없다. 이 이벤트가 바로 ⑥(시계열 기반 `causallyAffects` 발굴)이 필요한 이유다.
- **DRIFT는 잡히지만 늦다**: 29분(ST01 압력), 40분(ST04 진동), 74.5분(연구실 습도), 108분(창고 온도). 임계값을 넘을 때까지 기다리기 때문이다. SOP-002의 DRIFT 기준(기울기 > 0.1σ/분, 5회 이상)을 팀이 운영 정의로 합의하면 MAINT-01/02/06/08을 실행할 수 있고 지연이 줄어들 것이다.
- 오경보 1건은 ST02 전류가 13.5668 A로 한 표본만 WARN_HI(13.5)를 넘은 경우다.
- 이 결과는 이미 공개된 데이터를 재현한 것이며 미노출 평가가 아니다. 규칙 기반이라 학습·튜닝은 없다.

## 2026-11-04 경고 확인 옵션 실험

main 커밋 `6ce2c70`을 기준으로 원본 센서 자료의 해시를 확인하고 main 전처리기로 22개 센서의 211,200행을 재생성했다. 경고 구간만 같은 쪽 경계를 연속 두 표본에서 넘을 때 알리도록 선택할 수 있다. 표본 간격은 30초이며 정상 범위 복귀, 상한·하한 방향 전환, 시간 공백에서 확인을 다시 시작한다. `condition_start`는 첫 초과 시각, `trigger_at`은 확인 완료 시각이다. 기본값은 한 표본이다.

| 이미 알려진 이벤트 14건, 허용 지연 0분 | 기본 1표본 | 확인 2표본 |
|---|---:|---:|
| 전체 규칙 탐지 구간 | 102 | 91 |
| 경고 구간만 | 50 | 39 |
| 전체 탐지 이벤트 | 13/14 | 13/14 |
| 어떤 라벨 이벤트와도 겹치지 않은 경보 구간 | 1 | 0 |
| 전체 최초 탐지 지연 중앙값 | 0.5분 | 0.5분 |
| 경고 계열 최초 탐지 지연 중앙값 | 0.25분 | 1.25분 |
| ST02 전류 DRIFT 최초 탐지 지연 | 22분 | 40분 |

두 실행 모두 예측 파일을 봉인한 후 같은 평가기로 채점했다. 중앙값은 짝수 표본에서 중앙 두 값의 평균을 사용하도록 수정했다. 문서 규칙 43개 탐지 구간과 위험 규칙 9개 탐지 구간은 이벤트 ID와 시각까지 동일했다. 전체에서 ST01 압력 DRIFT도 29분에서 29.5분으로 늦어졌다. CORRELATED는 두 조건 모두 0/1이다. 라벨과 겹치는 것만으로 인과나 조치 효과를 판단할 수 없다.

이 데이터에서는 한 표본 경고를 일괄 억제하기에 ST02의 지연 비용이 크다. 두 표본 옵션은 경보 검토용 비교 설정으로 둔다. 다음 개발 후보는 첫 초과 시각을 조기주의로 노출하고 연속 관측 시 확인 경고로 승격하는 방식이다. 채택 전 별도 기간에서 미확인 주의 건수와 센서별 탐지 지연을 함께 평가한다.

```powershell
$env:PYTHONPATH='src'
..\.venv\Scripts\python.exe -m imaks_kg.detection.kg_rules --out kg_build/main_confirm2 --warning-samples 2
..\.venv\Scripts\python.exe scripts/evaluate_detector_events.py --run kg_build/main_confirm2
```

## 2026-11-05 조기주의와 확인 경고

`--warning-samples 2`로 실행하면 경계를 처음 넘는 표본에서 watch를 기록하고, 같은 방향으로 다음 30초 표본에서도 경계를 넘으면 confirmed를 기록한다. warning_transitions.json에서 센서, 규칙, 시작 시각(watch_at)으로 두 단계를 연결한다. 정상 범위 복귀·방향 전환·시간 공백에서 연속성이 끊긴다. 평가기는 결과의 해시를 확인한 뒤 warning_stages.json에 센서별 건수와 각 라벨 사건 안에서 최초로 기록한 단계별 지연을 저장한다.

| 주의 시작 시각 기준 구간 | 조기주의 | 확인 | 미확인 |
|---|---:|---:|---:|
| train | 5 | 5 | 0 |
| validation | 12 | 8 | 4 |
| test | 33 | 26 | 7 |
| 전체 | 50 | 39 | 11 |

미확인 11건은 ST02 전류 6건, 식당 온도 3건, 창고 온도 2건이다. 전체 주의 중 라벨 사건 밖에서 발생한 것은 1건이며 확인 경고는 0건이었다. 미확인은 연속 표본 조건의 판정이고, 사건 밖 알림은 라벨과의 시간 대조 결과다.

ST02 전류 DRIFT는 08:00 시작 후 08:22에 13.694 A로 첫 주의가 기록됐다. 08:39:30에 새로 시작한 주의가 08:40에 확인됐다. 최초 주의는 최초 확인보다 18분 앞섰고, 실제 승격된 구간의 확인 대기는 30초였다.

전체 규칙은 14건 중 13건을 탐지했다. 이전 두 표본 설정과 91개 탐지 구간 기록이 일치했다. 같은 기간의 오프라인 재생 결과이며 독립 기간 성능은 미검증이다. 탐지기 테스트 24개를 통과했다.

재현할 때는 앞 절 명령의 출력·평가 폴더로 kg_build/main_watch2를 지정한다.
